# Twinlab - Two-hour Glucose Digital Twin

**Happiest Health Reimagining and Reforming Healthcare in India Summit 2026 - Phase 1**

Twinlab is a Type 2 Diabetes proof of concept. It combines a simulated patient record with chronological wearable observations to predict glucose and flag a new elevated-glucose event **120 minutes ahead**. A clinician dashboard lets evaluators reveal the later observations and check each saved prediction.

## Problem statement and healthcare use case

Historical records omit a patient's changing glucose state. Sensor readings omit historical context. This PoC joins both into a virtual patient state updated at each simulated event. A doctor can inspect forecasts, risk flags, recent history, uncertainty and input sensitivity.

The scope is one localized outcome in Type 2 Diabetes, not a whole-body physiological model. Treatment recommendations and causal intervention effects are not implemented.

**Event definition:** glucose is at or below 180 mg/dL now and above 180 mg/dL exactly 120 minutes later. This endpoint target does not detect every transient crossing during the interval. The threshold is a demonstration definition, not treatment advice.

## Data fusion and sandbox rules

All training and replay data is **fully synthetic**, generated by train.py. No real EHR, restricted clinical database, actual genotype or live wearable account is used.

| Stream | Included fields | Artifact |
|---|---|---|
| Static EHR | Age, sex, diagnosis duration, HbA1c, BMI, hypothetical genetic marker | research/ehr.csv |
| Dynamic wearable | Five-minute glucose, sleep duration, steps, HRV, heart rate | research/wearables.csv |

Patient ID joins the streams. Eighteen features include historical values and current/past sensor lags, summaries, trend and clock time. Future measurements are never predictor inputs. Sleep duration is a previous-night summary available for that simulated day. Names and Indian cities are fictional labels; the generator is not an epidemiological model of India. Sleep stages are not modeled; relevant sensor signals are selected from the brief's examples.

## Technical stack and trained models

- Python 3.13.6, NumPy 2.3.2 and scikit-learn 1.9.0 for generation, training and evaluation.
- Glucose candidates: ridge, random forest and gradient boosting, plus persistence and linear-trend baselines.
- Event candidates: logistic regression and random forest classifiers.
- Deployed models: random forest regressor and random forest classifier, selected on separate validation patients.
- Separate calibration patients fit a residual interval and probability mapping. Validation F2 selects the alert cutoff, favouring recall.
- HTML, CSS, SVG and JavaScript run the exported fitted JSON models in the browser. Predictions are calculated; no fitting occurs on page load.

## Run the dashboard

From inside the project folder:

```bash
python -m http.server 4173 --directory dist
```

Open http://localhost:4173. Use a local server; opening index.html directly may prevent JSON loading. The pre-trained demo requires no ML packages and no frontend build step. Optional web fonts fall back to installed fonts.

[Hosted demonstration](https://twinlab-glucose-poc.pluckyiris4.chatgpt.site/)

1. Choose a virtual patient and time, or play the chronological replay.
2. Select **Correctly predicted spike** under **Jump to a measured example**.
3. Click **Reveal actual outcome** to compare the saved prediction with the observation two hours later.
4. Repeat with a false alarm and missed spike. Examples are curated demonstrations; aggregate scores use every test window.
5. Inspect **Data streams** and **Model & benchmarks**. Test gaps/noise and download snapshots, revealed forecasts and reports.

## Results and evaluation

90 synthetic patients have eight days of five-minute observations: **207,360 wearable records**. Cohorts are disjoint by patient: 54 train / 12 validation / 12 calibration / 12 test. Final evaluation uses **4,416 rolling forecasts**, spaced 30 minutes apart.

| Final synthetic-test result | Value |
|---|---:|
| Glucose MAE / RMSE | 10.04 / 14.03 mg/dL |
| Classifier recall: spikes caught | 71.3% |
| Classifier precision: alerts correct | 35.3% |
| Correct alerts / false alarms / misses | 211 / 386 / 85 |
| Residual-band test coverage | 89.7% |

Event metrics exclude origins already above 180. Counts represent overlapping forecast windows, not independent clinical episodes. Low alert precision is a material limitation; these results do not establish clinical accuracy or safety.

Other experiments: patient-group cross-validation, chronological holdout, one-stream regression ablations, sensor-gap/noise stress tests, subgroup diagnostics and 500 patient-bootstrap resamples. Regressor fixed-threshold event columns are separate from the dedicated dashboard classifier. See the [model card](jagjeet.work.16_National_Institute_of_Technology_Agartala/docs/MODEL_CARD.md) and dist/benchmark.json.

## Reproduce and verify

Install the pinned requirements in a virtual environment, then:

```bash
python -m pip install -r requirements.txt
python train.py
node check-model.cjs
python verify-data.py
node --check dist/app.js
node --check dist/model.js
```

Node.js 24 is used for checks. train.py regenerates data, fits candidates, selects on validation patients, calibrates and exports. Seed: 20261018. Headline scores reproduce in the recorded environment; parallel fitting can cause last-bit floating-point differences. The earlier pilot is disclosed in the model card.

check-model.cjs compares all **4,416** browser predictions and probabilities against Python exports, tests future isolation and gap handling, and reconciles event counts. verify-data.py checks record order, actual future labels, cohort IDs and hashes using Python's standard library. GitHub Actions runs technical checks, not submission certification.
